# LKS-SDD v2.0.1

**Fecha:** 2026-09-18. Release técnica estable del plugin; contrato consumidor 2.0 y método 2.0.0 sin cambios.

## Changelog

- Implementa la migración oficial 1.5/1.5.0 → 2.0/2.0.0 como una operación
  determinista, reversible y ligada a un preview completo con hash exacto.
- Conserva originales, evidencias, adjuntos enlazados, identidades, relaciones,
  locks y runtime legacy; registra la disposición de cada fuente en un recibo
  auditable.
- Detecta documentos legacy activos aunque el índice ya declare schema 2.0,
  bloquea el uso mixto y deja el proyecto en un corte verificable
  `migration-complete`.
- Añade continuidad selectiva por TASK: las incertidumbres semánticas no se
  convierten en autoridad v2 ni bloquean tareas independientes.
- Refuerza `migration-status` para validar mapping, hashes, archivos archivados,
  disposiciones, contadores, fingerprints, auditoría y ruta del recibo.
- Alinea las rutas de variantes: 1.5 usa `02-design`; 2.0 usa `03-solution`,
  con aprobaciones v2 bajo `00-control`.

## Compatibilidad

El plugin 2.0.1 conserva `schema_version: 2.0` y `method_version: 2.0.0`.
Actualizar el plugin no migra consumidores ni sustituye su runtime fijado:
la migración requiere diagnóstico, preview, autorización del hash exacto y
aplicación explícita.

La release no afirma aceptación conversacional de Codex/Copilot, piloto,
observadores externos, interoperabilidad Jira/Rovo/Entra ni instalación activa.
Esos canales permanecen separados y solo se consideran ejecutados con evidencia
propia.

Véanse [migración](../V2-MIGRATION.md), [compatibilidad](../COMPATIBILITY.md) y
[validación](../VALIDATION.md).

## Perfiles y locks

Se mantienen los perfiles active/candidate, sus locks y certificaciones exactas.
La actualización del plugin no sustituye el runtime fijado de un consumidor ni
promociona combinaciones candidate por similitud tecnológica.

## Validación y evals

La release queda condicionada al harness técnico del commit exacto, doble build
reproducible, validación de paquetes, checksums y aprobación específica
`quality/release-approval-v2.0.1.json`. Los canales humanos y de host permanecen
con su estado observado real.

## Vulnerabilidades conocidas y limitaciones

Los hashes no son firmas del editor, los roles declarados no autentican personas,
las transacciones no son atómicas globalmente y no existen locks distribuidos.
La migración no verifica código consumidor ni operaciones externas.

## Actualización

Para actualizar el plugin Copilot, usa la etiqueta `copilot-v2.0.1` y verifica
el paquete y sus checksums. Un proyecto consumidor 1.5 no se migra por actualizar
el plugin: sigue su runtime fijado hasta ejecutar la ruta de migración autorizada.

## Migración

Solo se soporta 1.5/1.5.0 → 2.0/2.0.0 mediante diagnóstico, preview y
autorización del hash exacto. Se conservan originales, evidencias, identidades,
relaciones y runtime histórico; las TASK con semántica pendiente requieren
reconciliación antes de continuar.

## Rollback

Conserva el paquete 2.0.0 verificado para una retirada explícita. En consumidores,
usa el recibo exacto y detente ante trabajo posterior; no muevas etiquetas ni
reactives autorizaciones históricas.

## Soporte

Release técnica sin nuevo SLA. Para incidencias, usa los canales de soporte,
seguridad y gobierno sin adjuntar credenciales ni datos de consumidores.

## Responsables

El responsable del proyecto autoriza esta publicación condicionada a los gates
técnicos. Mantenimiento, aceptación de producto y activación personal siguen
siendo responsabilidades separadas.
