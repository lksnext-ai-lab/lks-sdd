# Cobertura 0.16: evidencia de validación por TASK

## Diagnóstico diferencial de 0.15

0.15 ya aportaba `work status`, `work verify`, trazabilidad por TASK, `verification_subject`, EVID 1.2 inmutable, selección visual por TASK, separación G2/G3/G4, reporting de gestión, Jira por hitos y rollback transaccional. La evolución no duplica esos motores.

Los huecos observados eran contractuales: la revisión visual 1.1 acreditaba una ejecución pero no limitaba la cantidad ni describía suficientemente qué demostraba cada imagen; no existía una ficha TASK regenerable; el reporting mezclaba el último hecho verificado con problemas posteriores y escogía la primera TASK si no había una activa; Jira no distinguía los cinco hitos de validación pedidos; y la presentación exigía lecturas o resúmenes manuales adicionales.

## Diseño adoptado

La solución añade una capa derivada sobre los artefactos canónicos existentes:

1. `visual-review-evidence` 1.2 valida por TASK una política predeterminada 1–5, semántica, integridad y resultado.
2. EVID conserva el hecho histórico sobre una revisión; PROB/CKPT y una EVID posterior determinan la salud actual.
3. `work verify --record-evidence` escribe la EVID y todas las fichas TASK en una sola transacción.
4. `.lks-sdd/summaries/task-evidence/` es una proyección regenerable y queda fuera de `verification_subject`.
5. `work status` agrega estados sin presentar hashes, gates ni recibos en la vista management.
6. Jira recibe, como máximo, una proyección por hito relevante y nunca adquiere autoridad local.

## Contratos y schemas

- `schemas/visual-review-evidence-1.2.schema.json`: contrato cerrado de revisión visual. Cada captura enlaza TASK, AC, UX/VIS, superficie/ruta, estado previo, interacción, esperado, observado, modo, viewport, DPR, dimensiones reales, navegador, revisión/árbol, fecha/revisor, SHA-256, resultado y limitaciones.
- `schemas/visual-evidence-policy.schema.json`: política opcional de perfil. Si no existe, se aplican mínimo 1 y máximo 5. El máximo absoluto es 5.
- `schemas/task-evidence-summary-1.0.schema.json`: ficha derivada determinista, marcada expresamente como no canónica.

No cambia `schema_version: 1.5`, `method_version: 1.5.0` ni `verification-evidence` 1.2. La revisión visual histórica 1.1 permanece legible; una verificación nueva exige 1.2.

## Política visual

- Una TASK frontend, con unidad de interfaz, capability browser/frontend o referencias UX/VIS requiere entre una y cinco imágenes.
- Una TASK backend pura usa `not-applicable` y una justificación determinista.
- Se rechazan cero o más de cinco imágenes, sin fabricar capturas para completar cuota.
- Una imagen compartida puede cubrir varias TASK en una verificación conjunta; no se copia.
- Una corrección reemplaza una captura fallida del mismo estado mediante `supersedes` y conserva el historial anterior.
- Un sexto estado no se oculta: el validador recomienda dividir o priorizar la TASK y deja cobertura pendiente.
- Un defecto observado es evidencia ejecutada, pero su resultado es `failed` o `not-verified`.

## Ficha TASK derivada

La ficha contiene objetivo, estado del código, tests ejecutados, resultado técnico, cobertura visual, comportamientos demostrados/no demostrados, hallazgos, limitaciones, EVID relacionadas, revisión verificada, próxima acción y salud actual. Se genera para todas las TASK en una sola pasada, se valida antes del commit y se restaura o elimina si falla cualquier paso posterior.

No se escribe a mano, no altera EVID, no modifica `verification_subject`, no invalida builds y puede borrarse y regenerarse desde TASK, aceptación, tests, visual review, EVID y PROB.

## Historial y salud actual

Las dimensiones son independientes:

| Dimensión | Fuente | Valores relevantes |
|---|---|---|
| Verificación histórica | EVID inmutable | verificada / no verificada |
| Salud actual | EVID + hallazgos vigentes | healthy / compromised / pending-reverification / not-verified |
| Código | TASK/EXEC/CKPT | pendiente / activo / revisado / terminado |
| Tests | checks ejecutados o reutilizados | passed / failed / not-run |
| Entrega | G4 | pending / ready / delivered |

Un hallazgo posterior crea o mantiene un PROB, bloquea la salud actual y no edita la EVID anterior. `work correct` registra corrección y deja la TASK pendiente de re-verificación. `work resolve` exige una nueva EVID `verified` de la misma TASK antes de cerrar el hallazgo y completar.

## Reporting y Jira

`work status --view management` informa release/incremento, progreso, TASK terminadas/activas/bloqueadas/pendientes, verificación histórica, salud comprometida, hallazgos, cobertura técnica/visual, entrega, TASK activa real, próxima acción y decisiones humanas. Si no hay una TASK activa inequívoca, `current_task` es `null`.

La proyección Jira admite `verification-passed`, `verification-failed`, `finding-opened`, `correction-completed` y `reverification`. El comentario incluye TASK, resultado, pruebas, imágenes, hallazgos, revisión y próxima acción. Las imágenes usan rutas versionadas relativas; nunca rutas locales absolutas. Solo `verified` puede solicitar una transición compatible a Done.

## Regresiones y fixtures

El fixture `tests/fixtures/validation-evidence-v016.json` es totalmente genérico. `tests/test_validation_evidence_v016.py` cubre los límites 0/1/5/6, backend aplicable/no aplicable, duplicados, archivos y hashes, contradicciones, fallos observados, reemplazo, reutilización conjunta, salud posterior, TASK activa nula, neutralidad del sujeto técnico y Jira sin Done. Las regresiones de verificación existentes cubren materialización conjunta y rollback posterior a escritura.

## Benchmark 0.15 frente a 0.16

Escenario: una verificación frontend y una actualización administrativa posterior. Los tiempos de gates externos no se atribuyen al overhead.

| Métrica | 0.15 | 0.16 | Cambio |
|---|---:|---:|---:|
| Comandos | 4 | 3 | −25 % |
| Lecturas lógicas del proyecto | 5 | 2 | −60 % |
| Ejecuciones de tests iniciales | 1 | 1 | 0 % |
| Revisiones de navegador | 2 | 1 | −50 % |
| Escrituras documentales | 4 | 2 | −50 % |
| Interacciones humanas | 2 | 1 | −50 % |
| Operaciones Jira | 2 | 1 | −50 % |
| Duración administrativa aproximada | 18 min | 10 min | −44,4 % |

La medición reproducible vive en `scripts/benchmark_experience.py`. En una actualización puramente administrativa con `verification_subject` idéntico, 0.16 reutiliza gates y la ejecución adicional de tests es cero. Una modificación técnica invalida esa reutilización.

## Compatibilidad, atomicidad y límites

- Lectura compatible con proyectos 0.15 y EVID/revisiones visuales históricas.
- Ninguna migración destructiva ni reescritura de evidencia.
- Los artefactos derivados no participan en fingerprints.
- La materialización de EVID, manifest, traza y fichas conserva rollback completo.
- `validate-project`, trazabilidad, selección visual y reuse por `verification_subject` siguen vigentes.
- La interoperabilidad Jira/Rovo real, el piloto y los canales humanos permanecen `not-run`; la automatización no los presenta como superados.

La guía operativa de actualización está en `docs/MIGRATION-0.16.0.md`.
