# LKS-SDD 0.15 · experiencia de producto y fast path

## Resultado

0.15.0 mantiene Markdown como autoridad, el índice JSON como proyección, autorización exacta, transacciones atómicas, rollback, gates y evidencia inmutable. La mejora está en la interacción: el estado normal habla del proyecto y la tarea, y la mecánica completa queda bajo demanda.

No cambia `method_version: 1.5.0` ni `schema_version: 1.5`; actualizar el plugin no migra ni reescribe proyectos.

## Vistas

| Vista | Uso | Contenido |
|---|---|---|
| `management` | predeterminada | release, recuentos, tarea, resultado, pruebas, verificación, entrega, bloqueo, siguiente paso y decisión |
| `developer` | diagnóstico accionable | componentes, archivos, comportamiento, comandos, servicios, cambios e instrumentación |
| `audit` | trazabilidad completa | índice, IDs, huellas, autorización, ejecución, checkpoints, problemas, evidencia y diagnósticos |

```powershell
python scripts/lks_sdd.py status <project-root>
python scripts/lks_sdd.py status <project-root> --task TASK-001 --view developer
python scripts/lks_sdd.py status <project-root> --view audit --json
```

`status` no ejecuta Docker, builds, tests ni acciones externas y no modifica el proyecto. Management JSON contiene solo `project` y `current_task`; en el fixture representativo ocupa menos de 8 KB.

## Modelo comprensible

La vista deriva por separado desarrollo no iniciado/en curso/código terminado, pruebas, verificación pendiente/bloqueada/superada y entrega pendiente/realizada. Solo muestra problemas `active` aplicables; `resolved`, `superseded` e `historical` permanecen en audit. No se aceptan aliases legacy de estado.

Las decisiones exclusivas de producción no bloquean una operación local; se relegan como futuras. Una autorización exacta vigente no se vuelve a pedir.

## Fast path

```powershell
python scripts/lks_sdd.py work status <project-root> --task TASK-001
python scripts/lks_sdd.py work start <project-root> --increment INC-001 --task TASK-001
python scripts/lks_sdd.py work resume <project-root> --task TASK-001
python scripts/lks_sdd.py work resolve <project-root> --task TASK-001 --problem PROB-001 --cause "..." --evidence EVID-002
python scripts/lks_sdd.py work review <project-root> --task TASK-001
python scripts/lks_sdd.py work verify <project-root> --task TASK-001 -- <opciones de verify>
python scripts/lks_sdd.py work block <project-root> --task TASK-001 --reason "..."
python scripts/lks_sdd.py work complete <project-root> --task TASK-001
```

La fachada conserva los comandos bajos vigentes para diagnóstico y audit. `review`, `block`, `resolve` y `complete` componen transición, progreso, problema, índice y un único checkpoint material en una transacción con rollback conjunto; `complete` deriva los datos exactos de la evidencia verificada y no admite un cierre declarativo sin ella. Agrupa preview y apply cuando ya existe una autorización exacta, realiza como máximo una mutación local por hito y devuelve management. No amplía la autorización a despliegue, producción, promoción, merge, push, Jira fuera de política, aceptación o excepciones.

## Problemas y checkpoints

Los estados canónicos de producto son `active`, `resolved`, `superseded` e `historical`. `work resolve` conserva descripción y condición, registra fecha, causa, actor y evidencia en el historial y devuelve directamente a revisión si el código ya estaba terminado. `work resume` falla de forma segura mientras quede un problema activo. Los checkpoints se reservan para inicio significativo, pausa, bloqueo, handoff, revisión terminada, verificación y cierre.

## Sujeto técnico y reutilización

`experience_engine.verification_subject()` calcula un hash determinista de código, tests, migraciones, fixtures, dependencias/locks, Docker/build, configuración de artefacto, entrega, bindings/perfiles y contrato activo. Solo excluye rutas derivadas demostrables: caché/recibos/resúmenes, checkpoints y evidencia generada.

Si solo cambian exclusiones administrativas, `compare_subject()` produce una attestación de continuidad con revisiones y rutas; si cambia cualquier entrada técnica o existe duda, invalida la reutilización. La matriz automatizada cubre código, test, migración, configuración, Docker, lock, perfil y contrato.

## Caché y doctor

La caché usa claves por contenido, versión del plugin y namespace; no es autoridad, no vive en Markdown y una entrada corrupta es un miss seguro. Management no muestra hits/misses; developer/audit sí.

`python scripts/lks_sdd.py doctor <project-root> --quick` comprueba versión, integridad mínima del paquete, scripts, schema, Python, drivers, Docker solo cuando el perfil lo exige y Jira solo cuando la operación actual lo necesita. Nunca ejecuta la suite interna del plugin.

## Jira e instrumentación

Markdown continúa siendo autoridad y Rovo el peer outbound-only. `work sync-jira` presenta un único evento visible y conserva lectura fresca, duplicado, autorización, escritura, relectura, recibo y reconciliación como pasos auditables. Los IDs se observan; nunca se infieren por nombre. La interoperabilidad real permanece `not-run` sin piloto autorizado.

Developer/audit separan `plugin_overhead_ms`, `project_parse_ms`, `validation_ms`, `gate_execution_ms`, `external_sync_ms`, archivos, caché, gates, operaciones administrativas y confirmaciones. No existe telemetría externa ni persistencia de prompts, secretos o datos personales.

## Antes y después

Medición sobre el mismo fixture genérico de 13 tareas y 420 relaciones:

| Métrica | 0.14.2 | 0.15.0 |
|---|---:|---:|

| confirmaciones | no instrumentadas retrospectivamente | 0 para `work start` con AUTH exacta |
| mutaciones | no instrumentadas retrospectivamente | 1 transacción por hito `work` |

| parseos visibles | distribuidos entre 10 operaciones | una carga por invocación compuesta |
| validaciones administrativas | distribuidas entre comandos | validación integrada en la operación |
| tool calls administrativos | 10 | 4 |

Los tiempos 0.15 proceden de subprocess reales de la CLI pública sobre el fixture; no se inventa un tiempo retrospectivo para 0.14.2. Los gates, Docker, build, tests y sincronización externa se excluyen del overhead. Ejecute `python scripts/benchmark_experience.py --json` para una medición local nueva.

## Rollback

Cada mutación compuesta valida el resultado y restaura conjuntamente tablero, detalle, índice y checkpoint ante un fallo. El registro de verificación conserva además el rollback demostrado de EVID, trazabilidad, manifest, verification, last_delivery y ejecución. El rollback de distribución vuelve al bundle inmutable 0.14.2 y no reescribe consumidores.
