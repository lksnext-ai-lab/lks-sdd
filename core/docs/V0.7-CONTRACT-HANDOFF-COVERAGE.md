# Cobertura 0.7: contrato documental y handoff 1.1

Este documento describe la implementación de la adenda canónica 1.1 sin alterar las fuentes históricas. La release `0.7.0` sigue siendo candidate y no acredita los canales humanos o de piloto pendientes.

| Área | Implementación | Evidencia automatizable |
|---|---|---|
| Contrato por tabla | `schemas/document-contracts.json` declara cabeceras, propietario, estados, relaciones, cardinalidad, aplicabilidad y assets | `tests/test_contract_engine.py` y validación del contrato del plugin |
| Referencias | ID, listas y rango inclusivo `..`; `a` solo en compatibilidad 1.0; no hay expansión parcial ni `ART-*` activo en 1.1 | Pruebas unitarias del parser y del modelo |
| Estados | Naturaleza derivada del artefacto/prefijo y políticas de ciclo de vida por tabla | Casos válidos e incompatibles por política |
| Grafo activo | Modelo completo para auditoría y contrato activo por incremento con huella independiente | Regresiones con elementos y assets históricos |
| Dominios | Matriz separada para datos, identidad, seguridad, privacidad e integraciones | Validación de cardinalidad, aplicabilidad y prefijo objetivo |
| Handoff | Trazabilidad `preimplementation` sin evidencia obligatoria y `verification` con evidencia ejecutada | Pruebas de alcance vacío, cadena incompleta y cambio de fase |
| Readiness | `specification_readiness` separado de `automation_support`; puerta combinada conservadora | Perfil H0 validado, perfil alternativo documentable y perfil desconocido |
| Ayuda | Cobertura declarada, preflight estructural y readiness derivado, sin persistir aprobación | Pruebas de solo lectura y salida contextual |
| Migración | 1.0 → 1.1 fail-closed para cada `human_review_required`; `Identity` agregada se divide como tres dominios `pending`, sin referencias inferidas, para resolverse después en 1.1 | Pruebas de dry-run, bloqueo, apply real con validación, readiness bloqueado y recuperación |
| Calidad | Evidencia de catálogo resoluble, métricas passed/skipped/failed y skip crítico incompleto | `tests/test_quality_harness.py` |
| Empaquetado | Commit Git existente, igual a `HEAD`, árbol limpio, reporte candidate ligado y blobs leídos del commit | `tests/test_m5_pilot.py` y doble build reproducible |

## Compatibilidad

- Los proyectos 1.0 siguen validándose en modo compatibilidad y reciben una advertencia de migración.
- Los proyectos nuevos se crean con método `1.1.0`, esquema `1.1` y plugin `0.7.0`.
- La actualización del plugin no modifica proyectos consumidores. La migración requiere preview y autorización expresa; toda entrada de `human_review_required` se resuelve en los Markdown 1.0 y bloquea siempre `--apply` hasta repetir el preview con lista vacía. La `Identity` agregada no aparece en esa lista: genera identidad, seguridad y privacidad `pending` con motivo, valida tras el apply y bloquea readiness hasta resolverse en 1.1.
- Las vistas textuales de errores, `blockers` e `input_fingerprint` se conservan para consumidores anteriores; la salida añade diagnósticos estructurados y huellas diferenciadas.

## Límites

- Solo el perfil `WEB-FASTAPI-REACT-KEYCLOAK-PG` tiene automatización H0 empaquetada y validada. Otros perfiles pueden documentarse sin que eso se presente como soporte de implementación.
- La validación determinista no decide suficiencia semántica, autoridad humana ni aprobación de entrega.
- Los canales `definition-conversation`, activación, revisión documental y piloto conservan su estado real. Un canal `not-run` no se transforma en `passed` por esta cobertura.
