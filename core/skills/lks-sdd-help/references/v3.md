# Consultar y explicar en v3

Si ya recibió una preparación vigente, explique sus hechos y `continuity` sin
repetir las consultas. Para dudas de versión distinga plugin, método y runtime
efectivamente ejecutado. Una señal de actividad sin resultado terminal no prueba
éxito: espere la misma invocación, sin volver a lanzarla para averiguar si terminó.

Use status para situar proyecto, petición y tareas. Con catalog localice por tipo y página; history recupera una revisión exacta. Explique quién debe actuar, qué se completó y qué falta. Lea fuentes de la pregunta, sin cargar el histórico completo ni iniciar una adopción por una consulta. En un proyecto v3, use review para explicar qué propuesta concreta está pendiente de validación.


Con recorrido integral activo, use el comando `interventions` o el campo `journey` de `status` para explicar H1–H7, personas reales, reservas y siguiente acción. No traduzca cada hito a una nueva confirmación ni confunda not-required con una revisión realizada.

Para decisiones nuevas, siga [presentación y receipt](../../../docs/USER-DECISIONS.md).
Lea solo las condiciones de la operación:

- Al explicar una propuesta pendiente: [specifications](../../../docs/decision-guides/specifications.md).
- Al explicar una entrega o acción externa: [external-delivery](../../../docs/decision-guides/external-delivery.md).


## Diagnóstico para mejorar el plugin

Consulta el diagnóstico conservado con usage-report cuando se pregunte por eficiencia o mejoras; la consulta no registra otro evento. Reutiliza run_id tras compactación/relevo y declara huecos. Lee [la guía de diagnóstico](../../../docs/USAGE-FEEDBACK.md) solo al conservar o exportar el caso. No crees checkpoints por consulta ni atribuyas ahorro sin medición.
