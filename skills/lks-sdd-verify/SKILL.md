# Verify an LKS-SDD Increment with Codex

Verification produces evidence, not approval. Never classify a check as passed unless it actually ran and its result is available.

1. Read the project index, selected profile lock, increment, acceptance criteria, test strategy, traceability, implementation diff, and repository instructions.
2. Read the [verification contract](references/verification-contract.md). Resolve `<plugin-root>` as the directory containing `.codex-plugin/plugin.json` for this installed skill; never resolve `scripts/` against the consumer project. Run `python "<plugin-root>/scripts/lks_sdd.py" verify "<project-root>" --increment <INC-###> --plan --json` and explain applicable checks, side effects, prerequisites, and omissions. The plan is available only when `implementation` identifies that same increment with the selected `profile_id` and its status is `in-progress` or `completed`; an anticipatory `in-progress` plan never authorizes execution. A 0.6+ increment with an applicable interface always includes `visual-browser-review`.
3. Execute only after the implementation record for the requested increment is `completed` and explicit authorization is present with `--execute --authorize`. Never run a check while the implementation is absent, belongs to another increment, uses a profile inconsistent with `technology.selected_profile`, or remains `in-progress`, `not-started`, or `blocked`. Add `--containers` only when starting the local PostgreSQL/Keycloak stack is authorized and safe. For an applicable interface, provide reviewed browser evidence 1.1 with `--visual-evidence <local-json>`; bind it to the completed implementation, current UX/VIS baseline, viewports and screenshots as defined in the contract. Without it, the visual check remains `not-run` and the increment cannot be `verified`. Do not substitute a different command because a required tool is missing.
4. Review semantic acceptance, security, accessibility, performance, deployment, and rollback according to applicability. The deterministic runner covers the H0 technical checks but cannot prove business behavior by itself.
5. Record evidence with a stable `EVID-###` using `--record-evidence` only in the same authorized execution and only while that implementation record remains `completed`. Link it to requirements, acceptance criteria, the increment, and `TEST-###` rows; preserve raw sensitive logs outside canonical documentation and retain only the minimum safe result. The visual result freezes the review JSON, implementation/specification baseline, confirmed assets and each screenshot; project validation rechecks them.
6. Classify the result as `verified`, `verified-with-reservations`, or `not-verified`. Report failed, blocked, not-run, and not-applicable checks separately, with limitations and the smallest corrective action.
7. Delivery remains a separate human decision. For a client view, follow [client-view rules](references/client-view-rules.md) and use the controlled renderer only with confirmed, client-authorized sources.
