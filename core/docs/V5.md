# LKS-SDD 5

Versión preparada: 5.0.0. Tres tipos documentales persistentes: especificación de
capacidad funcional, definición de tarea y un único plan que evoluciona por tarea.
Los contratos históricos de `specs/canonical` se conservan intactos. La petición y
el diseño v5 aprobados para implementación están en `specs/proposed/v5` del proyecto
de desarrollo; no se cargan como contexto obligatorio de los consumidores.

## Proyecto y tarea

`docs/sdd/especificaciones/ID.md` describe comportamiento, reglas, permisos,
contratos y criterios estables de una capacidad; no se organiza por cada pantalla
o endpoint. Las reglas comunes se definen una vez y se referencian mediante
`depends_on`. `proyecto.md` contiene el contexto y la política transversal.

`docs/sdd/tareas/ID/tarea.md` expresa objetivo, alcance, criterios observables,
responsable, capacidades (`units`), políticas (`policies`) y autoridad disponible.
`plan.md` contiene enfoque técnico, pruebas, bases, progreso, decisiones, bloqueos,
resultados y siguiente paso. Una tarea compleja puede tener subtareas enlazadas con
`subtasks` y `parent`; cada subtarea conserva el mismo par documental. El contexto
normal lee solo la tarea, su plan, unidades transitivas, política y AGENTS.md.

Los Markdown usan un encabezado JSON entre líneas `---`, compatible con YAML.
`format` es `lks-sdd/5`; `kind` es `unit`, `task` o `plan`; `id` coincide con el nombre
canónico. El cuerpo sigue siendo Markdown legible. No hay documentos obligatorios
AUTH, EXEC, CKPT, EVID ni informe de cierre separado. `.lks-sdd/project.json` es un
índice derivado; `.sdd-work` contiene solo trabajo temporal y recuperación local.

## Decisiones y autoridad

Una orden humana de implementar dentro del alcance definido se registra una vez;
no requiere ratificaciones al preparar el plan, probar o actualizar progreso.
`authorize` registra actor, fuente de decisión y operaciones cubiertas
(`implement`, `consolidate`, `deliver`) ligadas al contenido actual de la tarea.
Es trazabilidad de autoridad aportada por el host, no autenticación de identidades.
Una ampliación material invalida esa cobertura; un cambio de progreso, una nueva
referencia de autorización, responsable o subdivisión interna no revocan la autoridad del padre. Las decisiones críticas pendientes bloquean la parte afectada.
No se presupone tecnología preferente. La publicación, instalación, commit, push
y comunicación con terceros necesitan autorización explícita que cubra la acción.

## Uso

`python <plugin-root>/scripts/lks_sdd.py --help` muestra el CLI. Todos los comandos
aceptan `--root PROYECTO`. En un consumidor fijado, `<plugin-root>` es el runtime de
`.lks-sdd/distribution-lock.json`; `doctor` comprueba integridad de núcleo y adapters.
Una instalación nueva del plugin no cambia automáticamente proyectos fijados.

| Acción | Comando y argumentos |
|---|---|
| Consultar | `context --task ID`, `status --task ID`, `validate [--task ID]` |
| Definir | `prepare --task ID --data argumentos.json` |
| Registrar autoridad disponible | `authorize --task ID --data decision.json` |
| Comprobar | `check --task ID --check NOMBRE` |
| Huella de entradas para proveedor | `fingerprint --task ID --check NOMBRE` |
| Importar resultado nativo | `import-result --task ID --check NOMBRE --source informe --data origen.json` |
| Esperar resultado externo | `wait-result --source informe --data limites.json` |
| Consolidar | `close --task ID --data cierre.json` |
| Registrar entrega | `delivery --task ID --data hechos.json` |
| Reanudar escritura interrumpida | `resume` |
| Inspeccionar binario sin decodificarlo | `artifact --source archivo.zip` |

`--data -` lee JSON por stdin sin crear archivos de argumentos. En `close`,
`documents` permite enviar el Markdown resultante por unidad directamente; `updates`
conserva la alternativa de referencias a archivos.

Los JSON de argumentos son una interfaz opcional para automatización, no nuevos
artefactos canónicos ni recibos obligatorios. El agente puede editar directamente
los dos Markdown o invocar las funciones del núcleo; no debe generar wrappers por
operación. `prepare` recibe `title`, `request`, `criteria` (lista), `units` (lista),
`owner` y opcionalmente `parent` y `paths` (rutas de alcance). `authorize` recibe `actor`, `source`, `scope`.
`close` recibe `updates` (unidad → ruta del Markdown resultante) y `facts` con los
campos de entrega que cambian: conserva los ya registrados y deja los ausentes como
`unknown`, sin pedir rellenar seis casillas en cada cierre. `init` recibe `project` y
`policy` explícitos (puede ser `{}` si no hay controles adicionales) y solo sirve
para proyectos nuevos sin SDD anterior. El CLI comprueba integridad automáticamente;
`doctor` separado se usa para diagnóstico o antes de ediciones directas.

## Pruebas proporcionadas y evidencia

El plan declara `checks` como mapa. Una comprobación local requiere `argv` (array,
sin shell), `inputs` (globs relativos que incluyan código, tests, configuración,
lockfiles y dependencias pertinentes), `environment` (identidad explícita) y
opcionalmente `environment_keys`, `timeout`, `max_age_seconds`. El resultado liga
esas entradas, adiciones/eliminaciones, contrato de tarea (sin autoridad, propietario
ni enlaces administrativos), política, versión del
intérprete y hash del ejecutable. El método no puede inferir dependencias omitidas:
el responsable debe revisar la cobertura de inputs y la identidad del entorno.
Nunca uses credenciales o secretos como identidad del entorno ni en argumentos.

Un test vigente se reutiliza sin ejecutarlo ni crear documentos. Un fallo o timeout
conserva estado y un único log temporal por comprobación, sustituido en cada fallo
y retirado cuando pasa; una edición ajena del log se conserva como conflicto.
Una modificación documental ajena a las
entradas no fuerza repetir tests; cambios en contratos pertinentes sí deben estar
incluidos. `no_checks_reason` permite un cierre documental justificado. Cada
criterio debe contrastarse con evidencia semántica; el runtime no certifica que el
criterio esté bien formulado ni que un comando abarque todo el comportamiento.

Los resultados externos declaran `provider`, `tool_version`, `environment`,
`inputs`, `result_format` (`junit`, `gitlab`, `sonarqube`) y, para GitLab, `commit`.
Se importan con `inputs` (huella previa), `provider` y `run_id`. La fecha `finished`
es la de ejecución original, nunca la de importación. Si el formato no la incluye,
`finished_at` debe aportar la fecha original con zona horaria desde el proveedor.
Una antigüedad desconocida no satisface `max_age_seconds`; reimportar el mismo informe
no renueva su vigencia ni modifica el plan. El host debe obtener
el informe original de la ejecución identificada; un fichero local no autentica
al proveedor. Un JUnit vacío o con skips, una pipeline no terminal o de otro commit,
o una puerta Sonar sin resultado no son verificaciones superadas. Para dependencia
u otros proveedores conserva el informe original y usa una comprobación explícita
que evalúe sus criterios; no simules éxito con un booleano manual.

Una caída de CI, VPN o credenciales se registra como bloqueo localizado. Una espera
puede hacerse en un único proceso con backoff; no se requiere polling del modelo.
El despliegue registra `delivery` y solo exige comprobaciones adicionales declaradas
en `proyecto.policy.deployment_checks`. Tanto `close` como `delivery` exigen la
misma autoridad de entrega y esas comprobaciones antes de registrar un despliegue
realizado. `not-run`, `pending` y `unknown` siguen siendo estados honestos sin
atribuir una acción externa. `proyecto.policy.required_checks` conserva controles
obligatorios de calidad; una migración no los convierte en simples notas. No ejecuta una regresión completa por defecto.

Cuando todos los criterios del padre están delegados mediante `criterion_links`,
los controles comunes acreditados por todos los hijos enlazados se reutilizan por
referencia. Se comprueban su cierre, alcance y entradas actuales; no se copian
resultados ni se repiten tests. Un criterio propio o una prueba obsoleta impiden
usar esa delegación como cobertura completa.

## Concurrencia y recuperación

El plan guarda `bases` (ruta → SHA256) de las capacidades que modifica. Antes de
consolidar, se comprueban todas las bases y resultados. Dos tareas sobre una unidad
pueden avanzar; la segunda debe conciliar la unidad si cambió. No actualices la base
sin revisar y conservar los cambios ajenos. Un lock local coordina este runtime;
no bloquea editores externos ni sustituye ramas, revisión y merges Git del equipo.

Una transacción usa un único journal temporal con estado anterior y posterior.
`resume` solo acepta archivos que sigan en uno de esos dos estados y entradas de
prueba vigentes. Cualquier edición posterior produce conflicto sin sobrescribirla.
El cierre retira solo temporales declarados bajo `.sdd-work/tmp`, con hash esperado.
Los binarios se referencian por ruta, tamaño, MIME y hash; no se abren como texto.

## Migración integral

Lectores directos para 1.5, 2.0, 3.0 y 3.1; nunca se ejecuta ni encadena un runtime
anterior. La migración es **definitiva y sin rollback**. No crea ZIPs de recuperación,
backups del modelo anterior ni retenciones por precaución. `migration-preview`
prepara el contenido útil, las referencias y la lista exacta de escrituras/retiradas.
`--data` admite `mappings` (UID → capacidad), `dispositions` para consumidores
externos y `resolutions` para conciliación explícita de política y tareas.

`resolutions.policy` expresa la política vigente revisada; `resolutions.tasks.ID`
puede aportar `criteria`, `checks`, `policies` y una justificación `no_checks_reason`
cuando corresponda. No son nuevos documentos duraderos: son entradas de una única
conversión. Se extraen criterios, comprobaciones ejecutables y controles conocidos
cuando el origen los expresa inequívocamente. Solo los bloqueos declarados en origen
se trasladan como bloqueos; faltar una configuración ejecutable no crea trabajo.
Los indicadores de reconciliación del método anterior se conservan como contexto,
sin exigir reconstruir checkpoints, observers o recibos. Las solicitudes y propuestas
se conservan como conocimiento, sin crear otra tarea por cada registro histórico.
Los registros de trabajo sin tarea propietaria van a `antecedentes.md`, fuera de
la política transversal que se carga automáticamente. Sus enlaces permiten ampliar
contexto cuando sea pertinente, sin arrastrarlos en todas las tareas nuevas.
La conversión no inventa aprobaciones ni renueva tests antiguos ni reabre tareas cerradas.
La preparación de comprobaciones se hace al retomar el alcance pertinente. La política
común mantiene `required_checks` y su `check_scopes` por rutas; `paths` de la tarea
permite excluir controles ajenos a ese alcance. Una ruta desconocida o ambigua no
exime del control. Esto no acredita resultados ni sustituye las reglas del proyecto.

Se retiran registros de control sustituidos, snapshots e inventarios sin uso futuro.
Se conserva conocimiento funcional vigente, decisiones útiles y evidencia singular
necesaria. Las reglas de negocio no se recortan para lograr un documento pequeño.
El criterio de eficiencia mide el conjunto documental: más operaciones de control
no deben añadir archivos, copias ni trazabilidad sin valor. Las especificaciones
pueden crecer cuando el producto necesita conocimiento adicional.

`migration-apply --preview SHA256` aplica la propuesta revisada y fija el núcleo v5
como parte explícita de convertir ese consumidor. Comprueba el nuevo modelo antes
de retirar las fuentes sustituidas. La actualización del plugin instalado no migra
ningún consumidor silenciosamente ni toca caches globales.

Tras interrupción usa `migration-resume` para continuar hacia v5. Los cambios ajenos
producen conflicto; se concilian, no se sobrescriben. El estado temporal contiene
solo hashes y salidas preparadas, no copias antiguas. Una vez terminada la conversión,
se eliminan staging y journal. `discard-preview` solo cancela una preparación que
no se ha aplicado; una conversión iniciada debe terminar. No se reescribe el historial
normal de Git. No existe `migration-rollback`.

Al completar la conversión se genera un único `docs/informe-conversion-sdd-v5.md`.
Compara archivos y bytes antes/después del alcance completo convertido, por
documentación, control, runtime, adjuntos e integraciones. Incluye archivos creados,
modificados, retirados y sin cambios, unidades, tareas, criterios y bloqueos pendientes.
El informe cuenta como un archivo adicional separado del árbol canónico; no contiene
copias antiguas ni inventarios por archivo. La reanudación conserva el mismo informe.
Es una fotografía de la conversión, no un registro que crezca con el uso del plugin.
Los volúmenes técnicos no acreditan por sí solos equivalencia semántica ni aceptación.

## Cobertura entre tareas

El padre conserva sus criterios aunque tenga subtareas. `criterion_links` en su
plan enlaza cada criterio delegado a `[{"task": "HIJO", "criterion": "C1"}]`.
El cierre comprueba que el hijo esté cerrado, que su alcance y sus pruebas sigan
vigentes y que el criterio exista. Los criterios restantes necesitan comprobación
propia o `criterion_dispositions` con una razón concreta. No se copian resultados
de hijos al padre. Las decisiones de alcance viven en la tarea; cambiar únicamente
la organización de ejecución no exige reautorizar al padre.

## Límites de evidencia

`implementation`, `verification`, `integration`, `publication`, `deployment` y
`acceptance` son hechos distintos. `not-run` y `unknown` son resultados válidos de
honestidad, no canales superados. Medidas del núcleo no son tiempo total del agente.
No infieras ahorro de tokens a partir de caracteres; `billed_tokens` queda `null`
cuando el host no lo observa. La ejecución de tests de adapters no sustituye una
sesión real de Codex/Copilot, un piloto humano ni la aceptación organizativa.
