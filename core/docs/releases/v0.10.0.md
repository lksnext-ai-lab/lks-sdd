# LKS-SDD v0.10.0

**Fecha:** 2026-08-26
**Estado:** candidate local; no publicada ni instalada

## Changelog

Véase la entrada `0.10.0` de `CHANGELOG.md`. La release añade tracking operacional 1.4, elección explícita `repository-only`/`jira-hybrid`, `ART-TRACKING`, previews y recibos externos. Mantiene Markdown como autoridad y las seis skills existentes.

## Compatibilidad

- Codex continúa siendo el único runtime soportado contractualmente.
- Los proyectos nuevos usan método candidate `1.4.0` y schema `1.4`.
- Los contratos 1.0–1.3 siguen validándose; las migraciones son de un salto.
- Jira requiere un peer Atlassian Rovo instalado y autorizado separadamente.
- El bundle no contiene MCP, cliente Jira, hooks, apps, agentes ni credenciales.
- No existe modo Jira-only ni sincronización bidireccional silenciosa.

La propuesta metodológica está en `specs/proposed/LKS-SDD_extension_tracking_operativo_v1.4.md`. Las siete fuentes de `specs/canonical/` permanecen byte a byte intactas; esta release candidate no equivale a aprobación corporativa de la propuesta.

## Perfiles y locks

Se conservan los diez perfiles y sus estados de 0.9.1: seis `active` sujetos a certificación exacta vigente y cuatro `candidate` no soportados. Esta evolución no modifica descriptores, capabilities, drivers, scaffolds, locks, gates ni certificaciones, porque el tracker es un eje operativo independiente de la arquitectura tecnológica.

## Validación y evals

La puerta final debe ejecutarse desde un checkout dedicado y limpio conforme a `docs/VALIDATION.md` y `docs/DISTRIBUTION.md`. Hasta registrar ese reporte, no se declaran aquí tests ni harness como superados.

El harness reserva 1.800 segundos para la suite unitaria integrada. Este margen evita falsos fallos por timeout cuando las validaciones de portabilidad, contrato y tracking superan diez minutos en Windows; no modifica los criterios de aceptación.

El corpus 0.10 y los fixtures sintéticos cubren selección de modo, previews, recibos, prevención de duplicados, autoridad, degradación, migración y privacidad. Los canales `definition-conversation`, `activation`, `document-review` y `pilot`, incluida la interoperabilidad real Rovo/Jira, permanecen `not-run`. Candidate puede mantenerlos opcionales; stable no.

## Vulnerabilidades conocidas y limitaciones

- No se ha ejecutado todavía un piloto contra una instancia Jira real.
- Rovo puede estar ausente, desconectado o tener permisos insuficientes; en ese caso el flujo falla de forma cerrada o queda degradado.
- No existe idempotencia nativa prometida por Jira: la prevención de duplicados usa el marcador namespaced `LKS-SDD-PROJECT: <project_id>; TASK: TASK-###`, búsqueda y recibo local.
- Mapping de workflows, transiciones, comentarios y adjuntos no están automatizados salvo que una operación exacta futura se implemente y verifique.
- Site, proyecto, keys y URLs pueden ser sensibles; sólo se persisten de forma saneada cuando son necesarias.
- La propuesta 1.4 aún no es una fuente canónica aprobada.
- No existe SLA ni soporte de producción.

## Actualización

Actualizar el bundle no migra proyectos consumidores ni instala Rovo. Tras verificar los cinco assets candidate y sus checksums, la fuente marketplace se actualiza de forma controlada; Codex debe reiniciarse y debe abrirse una tarea nueva. La conexión Rovo/Jira, si se usa, se prepara y autoriza por separado. Esta nota no autoriza publicación, instalación o activación.

## Migración

La ruta es explícita: `1.0 → 1.1 → 1.2 → 1.3 → 1.4`, un salto por operación. Cada apply exige preview, hash exacto, backup externo, autorización y validación posterior.

`1.3 → 1.4` añade `ART-TRACKING` y su índice sin crear issues, consultar Jira, registrar progreso, modificar AUTH/evidencia ni inventar una elección humana. Rechaza cualquier `EXEC-###` no terminal y conserva byte a byte los checkpoints históricos 1.3; los nuevos checkpoints usan 1.4. El salto histórico `1.2 → 1.3` sigue generando schema 1.3, método 1.3.0 y plugin 0.9.1.

## Rollback

El rollback de distribución vuelve al bundle 0.9.1 verificado, no mueve tags ni borra evidencia. La reversión de un proyecto migrado se decide separadamente y usa el backup/manifiesto de su operación. Los issues externos no se eliminan automáticamente; los bindings y recibos se conservan para reconciliación.

## Soporte

Las incidencias no sensibles y saneadas pueden comunicarse mediante GitHub Issues. Vulnerabilidades, URLs internas, payloads Rovo, datos personales, credenciales o contenido de cliente deben usar el canal confidencial definido fuera del repositorio. Véanse `SUPPORT.md` y `SECURITY.md`.

## Responsables

Method owner, product owner, maintainer, security reviewer, quality reviewer, workspace admin y support owner siguen pendientes de confirmación externa antes de ejecutar el piloto. No se inventan identidades ni un SLA.
