# LKS-SDD v0.9.0

**Fecha:** 2026-08-22
**Canal:** release candidate
**Alcance:** planificación integral, autorización delimitada y continuidad autónoma

## Changelog

La relación completa está en la entrada `0.9.0` de `CHANGELOG.md`. Esta versión añade el contrato de método 1.3 como séptima fuente canónica aditiva y no modifica retrospectivamente las seis fuentes anteriores.

## Compatibilidad

- Codex continúa siendo el único runtime soportado contractualmente.
- Los proyectos nuevos usan método `1.3.0` y esquema `1.3`.
- Los esquemas 1.0, 1.1 y 1.2 siguen validándose sin actualización automática.
- Las migraciones son explícitas y de un salto: `1.0 → 1.1 → 1.2 → 1.3`.
- Una ejecución nueva requiere 1.3 para conservar cobertura, autorización y checkpoint.
- No se añaden MCP, conectores, hooks, apps ni agentes ejecutables; se mantienen las seis skills.

## Perfiles y locks

El catálogo conserva diez perfiles cerrados en seis familias. Continúan active React/Vite estático, Angular estático, API FastAPI stateless, API FastAPI con Keycloak/PostgreSQL, Next.js SSR y sistema completo React; continúan candidate Angular SSR, sistema completo Angular, worker RabbitMQ y procesador Kafka.

`active` solo es `supported` con certificación exacta vigente de descriptor, capabilities, driver, scaffold, composición, gates y motor. 0.9 no cambia esos contratos ni presenta los candidate como soportados.

## Validación y evals

La puerta publicable incluye los seis validadores de skill, el manifiesto, los contratos 1.0–1.3, las siete fuentes canónicas, perfiles y certificaciones exactas, fixture manifest, pruebas unitarias, evals deterministas y harness candidate con perfil completo en Docker. Los resultados exactos se consignarán desde el checkout dedicado del commit de release; ningún canal `not-run` contará como superado.

En la validación previa a integrar se descubrieron 178 pruebas: 177 pasaron y 1 quedó `skipped` porque el entorno Windows no concedió el privilegio necesario para crear el symlink adversarial. Los evals deterministas pasaron 5/5. Ese `skipped` no se contabiliza como éxito; el reporte publicable del checkout limpio conserva el resultado y los canales no ejecutados con su estado real.

Los escenarios automatizados cubren obligatoriamente planificación parcial de `prueba-calculadora`, planificación completa, selección explícita de porción, pausa/reanudación, cambio de alcance, release incoherente, dependencia cancelada, ausencia de estimaciones y migración 1.2 → 1.3 reversible sin autorización inferida.

## Vulnerabilidades conocidas y limitaciones

- La baseline normativa y esta release continúan candidate; no son política corporativa aprobada.
- Los cuatro perfiles candidate siguen sin soporte automatizado certificado.
- El canal `definition-conversation`, las revisiones humanas, la activación y el piloto real permanecen `not-run` salvo evidencia externa expresa.
- Un checkpoint no demuestra por sí solo aceptación, gate superado, commit, merge, publicación, despliegue o promoción.
- El camino crítico queda indeterminado si el proyecto no confirma duraciones.
- Los responsables nominales, licencia definitiva, SLA y canal confidencial siguen siendo decisiones externas pendientes.

## Actualización

La release publica bundles y checksums, pero no instala ni activa el plugin. Tras verificar `SHA256SUMS`, `release-manifest.json` y `quality-report.json`, la actualización de una fuente de marketplace ya configurada y el reinicio de Codex requieren una autorización separada.

No edite manualmente la caché como mecanismo de actualización y no atribuya a una tarea ya abierta la carga de metadatos nuevos.

## Migración

Actualizar el plugin no modifica proyectos consumidores. La migración 1.2 → 1.3 exige dry-run, backup externo, hash coincidente y autorización. Añade `ART-PLANNING`, definición ejecutable ampliada, `active_tasks`, fingerprints, autorizaciones y ejecuciones vacías; marca la planificación como pendiente y no inventa tareas, cobertura, políticas incrementales, autorización, avance, evidencia ni checkpoint. Conserva el workflow histórico, pero una tarea legada `ready` queda bloqueada para ejecución mientras su `Definition status` sea `incomplete`.

Los proyectos 1.0 y 1.1 aplican primero los saltos anteriores. Cualquier `human_review_required` de 1.0 → 1.1 sigue bloqueando la escritura. No hay saltos implícitos ni múltiples en una sola operación.

## Rollback

La retirada del plugin sigue `pilot/ROLLBACK.md` y vuelve a la distribución candidate 0.8.0 verificada. No autoriza borrar documentación, código, evidencias, tareas, autorizaciones o checkpoints. Una migración 1.2 → 1.3 se revierte únicamente con su backup y rollback protegido.

## Soporte

Las incidencias no sensibles se canalizan según `SUPPORT.md`. Vulnerabilidades, secretos o datos de cliente no deben publicarse en Issues; el canal confidencial debe definirse antes del piloto.

## Responsables

Los roles nominales de método, mantenimiento, seguridad, calidad, publicación y soporte permanecen pendientes en `GOVERNANCE.md`. Esta nota no transforma roles propuestos en asignaciones aprobadas.
