# Cobertura 0.12 — catálogo granular y perfiles Microsoft Entra

## Resultado implementado

La versión 0.12.0 añade cuatro capabilities granulares y dos perfiles exactos candidate sin cambiar el método 1.5, el schema 1.5 ni las siete fuentes canónicas. La unidad certificable sigue siendo el perfil cerrado; no existe composición dinámica de capabilities.

| Área | Implementado | Límite actual |
|---|---|---|
| Catálogo | `CAP-OIDC-DISCOVERY-JWKS`, `CAP-OIDC-API-BEARER`, `CAP-OIDC-SPA-PKCE`, `CAP-ENTRA-CLAIMS` | Una capability aislada no es seleccionable ni soportada |
| API | `API-FASTAPI-ENTRA-PG-OCI`, discovery `jwks_uri`, issuer/audience/tenant, scopes/roles, 401/403, Alembic, PostgreSQL y OCI | Candidate; interoperabilidad real y certificación completa `not-run` |
| SPA | `WEB-REACT-VITE-ENTRA-STATIC`, MSAL Browser, Authorization Code con PKCE, callback/logout, sesión y scope de API | Candidate; acceso real, consent, conditional access y renovación `not-run` |
| Readiness | `automation_coverage` por binding con seis ejes y bloqueos de cualificación | No altera el estado estricto `automation_support` |
| Multiunidad | Frontend y backend se documentan con `UNIT/BIND` separados | No existe todavía un perfil de sistema Entra |
| Compatibilidad | Se conservan las seis certificaciones activas y los proyectos schema 1.0–1.5 | No se promociona ningún candidate |

La regresión automatizada `FX-52` demuestra que la cobertura granular nunca se presenta como soporte. El caso semántico `FX-53` exige preservar Microsoft Entra sin composición dinámica ni fallback a Keycloak y permanece `not-run` hasta su evaluación controlada.

## Evidencia local

- Validación estructural de los doce perfiles con `--allow-unvalidated`.
- Locks deterministas `validated=false` para los dos profiles Entra.
- Tests unitarios de discovery, `jwks_uri`, tenant, scopes/app roles, 401/403 y configuración SPA.
- Gates separados para interoperabilidad real, que fallan cerrado si falta input efímero autorizado.
- Regresiones que impiden presentar un candidate o un perfil no catalogado como implementable.

## Pendientes explícitos

- ejecución contra un tenant Entra real autorizado, sin persistir tokens;
- revisión de seguridad y comportamiento humano de login/logout/consent/conditional access;
- gate completo de composición y evidencia de entrega;
- decisión posterior sobre promoción a `active` o incorporación de un perfil de sistema.

Ninguno de estos pendientes se sustituye con Keycloak ni con pruebas sintéticas.
