# Cobertura 0.15: eficiencia y control continuo de calidad

## Hechos implementados

- `quality/test-suites.json` asigna cada `test_*.py` una sola vez a `fast`, `integration`, `package` o `profile`; el validador falla ante módulos omitidos, desconocidos o duplicados. `profile` cubre contrato y reutilización; Docker `execute` permanece como fase gobernada independiente.
- `tests/run_unit_tests.py` ejecuta hasta dos módulos aislados en paralelo, mantiene stdout como JSON, publica progreso y heartbeats por stderr, registra duraciones y mata el árbol de procesos ante timeout. Las 48 pruebas de tracking se reparten en cuatro shards deterministas de 12 para mantener margen estable frente al timeout de módulo sin elevarlo.
- `scripts/run_fast_validation.py` conserva los focos existentes y añade selección por `--changed-from`; las rutas no catalogadas caen en la suite de integración.
- El harness realiza preflight de fuente antes de cualquier hijo, ejecuta los cuatro tiers una vez y evalúa límites absolutos y deriva comparable mediante `quality/performance-policy.json`.
- El reporte 1.2 registra ejecución y rendimiento sin incorporar esos datos variables a ninguna identidad de build. El schema 1.1 permanece únicamente como evidencia histórica de calidad legible.
- La automatización de GitHub separa PR, `main` y tag. Ningún workflow publica, instala, crea tags ni usa secretos.

## Invariantes preservados

- Un timeout, `skipped`, `not-run`, canal incompleto o baseline no comparable nunca se convierte en `passed` por omisión.
- Los presupuestos temporales bloquean la fase correspondiente, pero no rebajan checks funcionales, perfiles ni inventarios del paquete.
- El mapa de impacto solo reduce feedback de desarrollo; la release ejecuta el inventario integral desde un checkout limpio.
- El runtime acepta exclusivamente proyectos schema 1.5/método 1.5.0 y no reescribe el `plugin_version` de procedencia. No se modifica ninguna fuente de `specs/canonical/`.

| `integration` | 480 s |

| candidate sin Docker `execute` | 900 s |

Una ejecución comparable también falla si supera la baseline en más del 20 % y 30 segundos. Una baseline solo cambia mediante edición deliberada, razón documentada, tres ejecuciones limpias comparables y revisión del diff.

## Límites

- La baseline temporal inicial se completa únicamente tras tres ejecuciones limpias del commit de release en el entorno de referencia; mientras esté vacía siguen siendo bloqueantes los límites absolutos.
- Los canales semánticos, humanos, de piloto, Rovo/Jira real y Microsoft Entra real conservan sus estados `not-run`. Esta mejora del runner no aporta esa evidencia.

El `skipped` no se presenta como evidencia ejecutada: el comportamiento equivalente de rechazo de rutas enlazadas sí queda cubierto en otros tests, pero la variante de symlink visual necesita un runner con privilegio de creación de enlaces para pasar como ejecutada.
