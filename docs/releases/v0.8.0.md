# LKS-SDD v0.8.0

**Fecha:** 2026-08-21
**Canal:** release candidate
**Alcance:** gobierno de entrega, planificación trazable y arquitectura multiperfil

## Changelog

La relación completa está en la entrada `0.8.0` de `CHANGELOG.md`. Esta versión incorpora el contrato de método 1.2 sin reescribir las cinco fuentes históricas y añade una sexta extensión canónica preservada por hash.

## Compatibilidad

- Codex continúa siendo el único runtime soportado contractualmente.
- Los proyectos nuevos usan método `1.2.0` y esquema `1.2`.
- Los esquemas 1.0 y 1.1 siguen validándose sin actualización automática.
- Las migraciones son explícitas y de un salto: `1.0 → 1.1 → 1.2`.
- No se añaden MCP, conectores, hooks, apps ni agentes ejecutables.

## Perfiles y locks

El catálogo separa familias no seleccionables, capabilities reutilizables, perfiles cerrados certificables y bindings por unidad desplegable. Incluye diez perfiles en seis familias:

- active: React/Vite estático, Angular estático, API FastAPI stateless, API FastAPI con Keycloak/PostgreSQL, Next.js SSR y sistema completo React/FastAPI/Keycloak/PostgreSQL;
- candidate: Angular SSR, sistema completo Angular/FastAPI/Keycloak/PostgreSQL, worker RabbitMQ y procesador Kafka.

`active` no basta para declarar soporte. Cada perfil activo debe mantener una certificación exacta vigente de descriptor, capabilities, driver, scaffold, composición, gates y motor. Los perfiles candidate son visibles y documentables, pero bloquean automatización hasta completar esa certificación.

## Validación y evals

La puerta de la release comprende los seis validadores de skill, el manifiesto, el contrato 0.8, las seis fuentes canónicas, el inventario de diez perfiles, las certificaciones exactas de los perfiles activos, fixtures, pruebas unitarias, evals deterministas y gates completos en Docker. FX-22–FX-27 cubren las garantías nuevas de forma automatizada; el corpus conversacional 0.8 de FX-01/20/21 es independiente del 0.7 y conserva `not-run`. La evidencia semántica, humana y de piloto no se infiere de esas pruebas.

Los resultados concretos de una candidate publicable deben proceder de un checkout dedicado, limpio y ligado al commit de release. Una ejecución sobre este árbol de desarrollo es evidencia de pre-release, no un asset publicable.

## Vulnerabilidades conocidas y limitaciones

- La baseline normativa y la release continúan en estado candidate; no son política corporativa aprobada.
- Los cuatro perfiles candidate no garantizan todavía implementación/verificación reproducible.
- El canal `definition-conversation` carece de importador de resultados y mantiene bloqueada la promoción a stable.
- El piloto M5, los responsables nominales, la licencia definitiva, el SLA y el canal confidencial siguen pendientes de decisiones externas.
- Un gate técnico no autoriza merge, despliegue ni promoción sin la autoridad definida en el proyecto.

## Actualización

Actualizar el marketplace y activar el plugin son operaciones separadas. Tras verificar los assets y checksums de una release publicada, actualice la fuente del marketplace mediante el mecanismo soportado por la versión local de Codex, reinicie la aplicación y abra una tarea nueva. No edite manualmente la caché como mecanismo de actualización.

Este repositorio no instala ni activa automáticamente la candidate.

## Migración

Actualizar el plugin no modifica proyectos consumidores. Para un proyecto 1.1, ejecute primero el dry-run hacia 1.2; revise el gobierno, arquitectura, bindings, planes y tareas propuestos; aplique únicamente con backup externo, hash coincidente y autorización. Los pendientes creados no son decisiones confirmadas.

Los proyectos 1.0 deben cerrar primero el flujo 1.0 → 1.1. Cualquier `human_review_required` bloquea esa aplicación antes de escribir. No existe salto 1.0 → 1.2.

## Rollback

La retirada del plugin sigue `pilot/ROLLBACK.md`. Revertir o retirar una versión del plugin no autoriza a borrar documentación, código, evidencias o migraciones de proyectos consumidores. Una migración aplicada utiliza su propio manifiesto de backup y rollback protegido.

## Soporte

Las incidencias no sensibles se canalizan según `SUPPORT.md`. Vulnerabilidades, secretos o datos de cliente no deben publicarse en Issues; el canal confidencial debe definirse antes del piloto.

## Responsables

Los roles nominales de método, mantenimiento, seguridad, calidad, publicación y soporte permanecen pendientes en `GOVERNANCE.md`. Esta nota no convierte roles propuestos en asignaciones aprobadas.
