# Cobertura 0.8: gobierno de entrega, tareas y arquitectura multiperfil

Este documento describe la implementación de la extensión canónica 1.2. La release `0.8.0` permanece candidate: automatización técnica verificada no equivale a aprobación corporativa, ejecución de piloto ni promoción a `stable`.

## Artefactos canónicos 1.2

Los proyectos nuevos materializan veinte documentos de núcleo más `.lks-sdd/project.json`. A los artefactos 1.1 se añaden como obligatorios:

- `docs/lks-sdd/04-delivery/delivery-governance.md`;
- `docs/lks-sdd/04-delivery/plans.md`;
- `docs/lks-sdd/04-delivery/tasks.md`;
- `docs/lks-sdd/04-delivery/task-detail.md`;
- `docs/lks-sdd/03-solution/architecture.md`, ya no superficial u opcional para el handoff 1.2;
- `docs/lks-sdd/06-operation/deployment.md`, con entornos, promoción, recuperación y evidencia.

Los Markdown siguen siendo canónicos. El índice contiene referencias operativas a plan/tarea activos, gobierno, unidades y bindings, pero no persiste snapshots derivados de readiness o bloqueos.

## Estados y control de tareas

El tablero admite `backlog`, `ready`, `in-progress`, `blocked`, `in-review`, `done` y `cancelled`. El comando de transición:

1. valida el proyecto y el estado de origen;
2. valida que la transición pertenezca al grafo permitido;
3. comprueba requisitos específicos del destino;
4. genera preview y hash de autorización;
5. escribe tablero y detalle de forma atómica solo con autorización coincidente.

Una tarea bloqueada debe enlazar al menos un `PROB-###` abierto. Una tarea `done` debe contener gates superados, evidencia, revisión, build, digest y entorno; no se admite completar por edición cosmética del tablero.

## Modelo multiperfil

El catálogo 0.8.0 incluye perfiles React y Angular estáticos, API-only stateless, API con OIDC/PostgreSQL, SSR/Next.js, SSR/Angular, sistemas web completos React y Angular, worker RabbitMQ y procesador Kafka.

Los perfiles React estático, Angular estático, API stateless, API OIDC/PostgreSQL, Next.js SSR y el sistema completo React se declaran `active`. Los equivalentes Angular SSR/sistema completo y los perfiles event-driven RabbitMQ/Kafka se entregan como `candidate`: disponen de descriptor, locks, scaffold y gates, pero no son `supported` hasta obtener certificación completa.

Las capabilities reducen duplicación, pero no son unidades de homologación. El gate de composición se ejecuta sobre el perfil cerrado. La certificación conserva hashes exactos de descriptor, driver, scaffold, composición, capabilities, gates y motor; cualquier deriva invalida el soporte.

## Implementación y verificación

Readiness 1.2 evalúa por separado:

- `specification_readiness`;
- `delivery_readiness`;
- `automation_support` de todos los bindings aplicables.

La preparación opera sobre la tarea y sus unidades, materializa únicamente scaffolds de perfiles certificados, protege colisiones, exige autorización y ofrece rollback. El mismo apply sincroniza de forma atómica tablero y fichas de las tareas seleccionadas (`ready → in-progress`), rama, revisión inicial, actor, fecha e historial; cualquier deriva posterior al preview invalida su hash. La verificación resuelve todos los drivers aplicables, ejecuta sus gates y liga la evidencia a la revisión y al artefacto exactos.

G4 no se deduce de G3. La promoción requiere evidencia del entorno destino, build y digests, smoke/observabilidad, recuperación y autoridad definida por el proyecto.

## Compatibilidad y migración

- 1.0 y 1.1 continúan validándose con sus reglas históricas.
- La migración 1.1 → 1.2 es explícita, reversible y de un solo salto.
- La migración crea los nuevos documentos y campos, pero conserva gobierno, bindings y tareas como pendientes cuando no existe una decisión confirmada.
- No se fabrican revisión verificada, build, artefactos, despliegue o aprobación.

## Límites no cerrados por esta release

- Los perfiles candidate no están soportados aunque sus contratos sean válidos.
- Los canales semánticos, humanos y de piloto no ejecutados permanecen `not-run`.
- Merge, despliegue, promoción y cambios de política requieren autorización humana externa.
- La release no instala el plugin, no publica assets y no modifica proyectos consumidores automáticamente.
