# Implement an LKS-SDD Increment with Codex

Implement only the requested increment. A `ready` result is necessary but does not replace the user's explicit authorization to change code.

1. Read `.lks-sdd/project.json` and the indexed Markdown. Confirm the active increment and `TASK-###` slice, plan/release, delivery governance, deployable units and bindings, included/excluded scope, requirements, acceptance, tests, dependencies, blockers, interface applicability, and confirmed `UX-###`/`VIS-###` inputs.
2. Read the [implementation contract](references/implementation-contract.md). Resolve `<plugin-root>` as the directory containing `.codex-plugin/plugin.json`; never resolve `scripts/` against the consumer project. Run `python "<plugin-root>/scripts/lks_sdd.py" implement "<project-root>" --increment <INC-###> --task <TASK-###> --dry-run --json`. Stop if specification/delivery readiness, any exact profile binding/certification lock, governance, or adopted baseline is invalid.
3. Present planned files, task transitions and collisions. Apply the scaffold only after explicit authorization, using the returned preview hash with `--apply --authorize --preview-hash <hash>`; use `--actor` and `--date` when the recorded transition must identify a different authorized actor or effective date. The same atomic apply moves each selected `ready` task to `in-progress` in both board and detail, records branch/start revision/history, and materializes the exact per-binding locks. The preview is bound to `active_contract_fingerprint` (`input_fingerprint` remains a compatible alias); a change to an active Markdown input, task record or active prototype image requires a new assessment and preview, while historical rows remain auditable without invalidating the active contract. Preserve existing files; integrate an existing `.gitignore`, README, AGENTS instructions, pipeline, or application structure as a separate reviewed change.
4. Implement the smallest vertical slice that satisfies the linked acceptance criteria. When the interface is applicable, treat the confirmed screens, flows, direction and prototype assets as implementation inputs, not optional inspiration. Do not silently reinterpret or replace a validated visual baseline. Keep business rules out of transport boundaries, avoid speculative infrastructure, and do not expand the increment to unrelated cleanup.
5. Add or update tests linked to the documented `TEST-###` identifiers. Inspect repository commands before executing them; obtain separate authorization for commands with material side effects not already implied by the implementation request.
6. Keep the canonical task board and independent task detail synchronized. Use the controlled `tasks transition` command for workflow state, health, progress, blockers, owner/revision/build/environment fields and history. Do not mark `done` without `EVID-###`, exact revision, build ID, immutable artifact digest, environment, and passed gates.
7. Update affected Markdown and the operational index without turning observed behavior into a requirement. Keep `implementation.status` as `in-progress` while requested work remains; use `blocked` if it cannot continue. Only when the selected slice is genuinely complete set it to `completed`, preserving its `task_ids`, `profile_bindings`, exact lock hashes, start revision, branch, complete `changed_paths`, and evidence identifiers. Leave unexecuted verification as `not-run`.
8. Hand off to `$lks-sdd-verify`. Its plan may anticipate checks while the same implementation is `in-progress`, but it cannot execute or record evidence until `completed`. Do not classify the slice as verified from implementation tests alone.

Implement only exact closed profiles whose descriptor, driver, scaffold, certification evidence, composition digest, and consumer lock agree. A family, capability set, candidate profile, or arbitrary technology mixture is documentable but not automatically implementable.
